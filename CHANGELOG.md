# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to
[Semantic Versioning](https://semver.org/spec/v2.0.0.html). Versions before 1.0.0 may contain breaking changes;
they are marked **Breaking** with the steps to take.

## [0.0.5] - Unreleased

### Added

- GitOps key rotation for tenant keys. `SopsTenant` `spec.startRotation: true` starts a rotation once every
  `SopsSecret` of the tenant is `Decrypted`; the operator creates the next key in `<tenant>-sops-keys-next`.
  Setting it back to `false` completes the rotation once every `SopsSecret` decrypts with the next key: the next
  key replaces the current key and `<tenant>-sops-keys-next` is deleted. No private key leaves the cluster.
- `SopsTenant` status: `publicKey`, `rotation` (`phase`, `startedAt`, `nextKeySecretName`, `nextPublicKey`,
  `migrated`, `pending`, `pendingSecrets`) and `lastRotation` (`startedAt`, `completedAt`, `previousPublicKey`),
  and the `LAST ROTATED` printer column.
- `SopsTenant` condition `Rotated` with reasons `RotationRefused`, `RotationPending`, `RotationBlocked`,
  `RotationComplete`, `RotationAbandoned` and `NextKeyMissing`.
- `SopsSecret` `status.rotation`: during a rotation, the `sops.age` entry that adds the next key to the file.
- `SopsSecret` reason `NextKeyRequired`: during a rotation, a new or changed file must be encrypted for the next
  key too.
- `SopsTenant` reason `KeyMismatch`: the key Secret no longer holds the key recorded in `status.publicKey`, for
  example after restoring an old backup.
- `scripts/encrypt.sh` encrypts a plaintext `SopsSecret` file in a GitOps directory.
- `scripts/rotate.sh` adds the operator-prepared next-key entry to every `SopsSecret` file of a tenant and the
  next key to the `.sops.yaml` files sops uses for them, and removes the old key after the rotation completed.
- Output Secrets are watched (metadata only) as the tenant identity: a deleted or changed output Secret is
  restored at once instead of at the next resync. Its labels and annotations come only from
  `spec.template.metadata`.

### Changed

- **Breaking:** the ClusterRole `sops-tenant-secret-reconciler` (`create`, `update`, `list`, `watch` on Secrets)
  replaces `sops-secret-writer`. With `list` and `watch`, the tenant identity can read the Secrets in the
  namespaces granted to it. Until a namespace binds the new role, its `SopsSecret`s report `AccessDenied` naming
  the role, and existing Secrets stay as they are.
  **Action:** in each application namespace, bind `sops-tenant-secret-reconciler` to `<tenant>-sops-tenant`
  (see the README, onboarding step 2c), then delete the bindings to `sops-secret-writer`.
- The tenant key Secret holds only the private key: generated `age.agekey` has no comment lines and `age.pub` is
  no longer written. Read the public key from `SopsTenant` `status.publicKey`. An existing `age.pub` field is
  ignored, and keys generated by earlier versions keep working.
  **Action:** if tooling reads `age.pub` from the key Secret, read `status.publicKey` instead.
- `sops-key-owner` also grants `update` and `delete` on Secrets, used only to complete a key rotation or remove
  an orphaned next key. Existing bindings need no change.
- `AccessDenied` on a `SopsSecret` names the ClusterRole to bind and the Secret verbs it needs.

### Removed

- The ClusterRole `sops-secret-writer`.
- The `KeyInvalid` check for an `age.pub` field that does not match the key file.

### Security

- A `SopsSecret` can no longer write a Secret named `<tenant>-sops-keys` or `<tenant>-sops-keys-next` of an
  existing tenant in its namespace (`Conflict`), so an output Secret cannot pose as a tenant key.

## [0.0.4] - 2026-10-14

### Changed

- **Breaking:** the tenant key Secret is named `<tenant>-sops-keys` instead of `<tenant>`, and reported in
  `SopsTenant` `status.keySecretName`.
  **Action:** before upgrading from 0.0.3, copy the Secret `<tenant>` to `<tenant>-sops-keys` in the tenant
  namespace; otherwise the operator generates a new key and files encrypted for the old key no longer decrypt.

## [0.0.3] - 2026-10-14

### Added

- The operator creates each tenant's ServiceAccount, `<tenant>-sops-tenant`, and reports it in
  `status.serviceAccountName`.
- The ClusterRole `sops-operator-tenant` (`create`, `impersonate` on ServiceAccounts), bound to the operator in
  each tenant namespace.

### Changed

- **Breaking:** onboarding is RoleBindings only, per tenant: `sops-operator-tenant` to the operator and
  `sops-key-owner` to `<tenant>-sops-tenant` in the tenant namespace, and `sops-secret-writer` to
  `<tenant>-sops-tenant` in each namespace the tenant may write to. The operator has no cluster-wide
  ServiceAccount permissions.
  **Action:** onboard each tenant again with these bindings.
- The tenant admin may create the two tenant-namespace RoleBindings; namespace grants stay with the cluster
  admin.
- Tenant names are limited to 63 characters.

## [0.0.2] - 2026-10-14

### Added

- Upgrade tests along the channel graph of the catalog.

### Changed

- Events are recorded through the `events.k8s.io` API.
- Releases never overwrite a published image tag, and each catalog publish gets an immutable tag.

## [0.0.1] - 2026-10-12

### Added

- `SopsTenant` and `SopsSecret` custom resources, installed through OLM.
- Decryption of SOPS files in the cluster with a post-quantum age key per tenant, generated by the operator or
  brought by the tenant admin.
- Zero standing privileges: every key read and Secret write is an impersonated call as the tenant's identity.
- Ciphertext bound to its destination: the encrypted scope must match the `SopsSecret`'s namespace and name.
- Write-only output Secrets, tracked by the UID of the Secret the operator created.
